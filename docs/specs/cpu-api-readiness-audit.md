# SIG-106: CPU API readiness audit

Source: `origin/littlealan/gpu-synthesis-worker` at `7f62d9d`. This is a read-only audit of the code on that branch against SIG-105's intended CPU, request-billed API. The synthesis dispatch/worker work described in SIG-105 is not yet on this branch. “Move” below means that the path must run in the synthesis worker before the API loses its GPU. Production has `BACKEND_USE_STORAGE=true` and `BACKEND_EXPORT_MIX_ENABLED=false` (`env/prod.env:18-20`). No deployment or production run was performed.

## 1. GPU and MCP-GPU use

| file:line | What it is | Impact on CPU request-billed API | Suggested fix |
| --- | --- | --- | --- |
| `src/backend/mcp_client.py:934-945`, `src/mcp_server.py:38-61` | The complete tool map: `synthesize` and `save_audio` are GPU tools; parse/reparse, solfege edits, preprocessing and voicebank metadata are CPU tools. | With `MCP_GPU_ENABLED=false`, GPU calls raise `McpWorkerUnavailableError` (`mcp_client.py:1088-1097`). CPU tools can remain on the API, subject to CPU worker capacity. | Route both GPU calls through the synthesis job worker; retain CPU tools where the API still needs them. |
| `src/backend/orchestrator.py:694-720`, `src/backend/orchestrator.py:791-809` | `_synthesize` calls GPU MCP `synthesize`, then GPU MCP `save_audio`; it also writes a local lossless WAV for MP3 output at lines 759-769 and uploads results at 794-809. | The current API synthesis task fails without GPU, even if the MCP process itself is disabled. Output files created in the worker cannot be read from the API's disk. | Move the whole render/encode/upload path to the GPU worker; publish Storage paths in the job. |
| `src/backend/orchestrator.py:1635-1727`, `src/backend/orchestrator.py:8335-8439` | The current job prepares instrumental MIDI and then calls `_synthesize`. MIDI generation itself uses local MusicXML and CPU code. | MIDI is part of the job and must not become a separate API background stage; local paths will not cross service instances. | Keep MIDI inside the single worker job and upload/recover its artifacts before completion. |

The model wrappers are synthesis-only and should not load on the CPU API. | Keep CPU ONNX Runtime only if CPU paths require it; verify the CPU image imports the API without loading synthesis models. |

## 2. Work that outlives a request

| file:line | What it is | Impact on CPU request-billed API | Suggested fix |
| --- | --- | --- | --- |
| `src/backend/main.py:490-500` | Three startup branches schedule the same `asyncio.to_thread(_log_onnx_providers)` diagnostic. | It may stall indefinitely after startup when CPU is throttled; diagnostic logs can arrive late or be lost. | Run it within a request or make it optional/nonessential on the CPU API. |
| `src/backend/main.py:1303-1335`, `src/backend/main.py:1997-2168` | Export mix is queued with `create_task` after returning a job ID; its render, Storage upload and credit settlement continue in the API process. | Request billing can throttle or terminate this task, leaving a reserved credit/job unfinished. Production currently disables the endpoint, but enabling it on this API is unsafe. | Keep it disabled for the CPU move; redesign as a request-bound durable worker before enabling. |
| `src/backend/orchestrator.py:887-959`, `src/backend/orchestrator.py:1635-1803` | `_start_synthesis_job` creates an API-local synthesis task after the chat response and tracks it by session. | It can stall or die outside a request; it also requires the GPU. | Dispatch one durable synthesis Cloud Task and run MIDI, render, upload and atomic settle/complete in the GPU worker request. |
| `src/backend/orchestrator.py:1010-1042`, `src/backend/preprocess_dispatch.py:69-79` | Inline preprocess creates an API task; local HTTP dispatch creates a retry task. Production Cloud Tasks dispatch is request-bound (`preprocess_dispatch.py:69-73`). | Inline/HTTP modes are not safe as unattended API work under request billing; production Cloud Tasks mode avoids that dependency. | Keep production preprocess in Cloud Tasks mode; treat inline/HTTP as local-only. |
| `src/backend/orchestrator.py:1275-1295` | Preprocess lease heartbeat is created while the worker request runs and canceled in its `finally`. | Safe only while the Cloud Task HTTP request stays open; an inline API preprocess would be throttled. | Keep heartbeat inside the worker request. |
| `src/backend/orchestrator.py:1333-1362`, `src/backend/orchestrator.py:301-340` | `_await_billing_finalization` creates and shields per-job settlement/release work; shutdown cancels tracked jobs and waits for finalizers. | API-local finalization after a response or instance loss is not a durable guarantee. | Keep settlement/release in the worker request and use idempotent Firestore transactions/retry state. |
| `src/backend/orchestrator.py:1419-1443` | Action-required finalization briefly creates a message-render task and a shutdown-wait task, then cancels/gathers both. | Safe only while its enclosing synthesis request remains active; it cannot be left on a throttled API. | Move with synthesis finalization to the worker request. |
| `src/backend/orchestrator.py:5675-5714` | A preprocess repair notice is created with `create_task` and explicitly canceled/gathered before planning returns. | This is request-scoped when planning runs in a worker request; it is not a durable job boundary. | Keep it within the worker request and preserve the await/cancel cleanup. |
| `src/backend/mcp_client.py:957-995`, `src/backend/lifecycle.py:56-68` | MCP startup uses a daemon thread; shutdown prestarts a control executor. Neither is tied to a normal HTTP request. | On a throttled API, boot-time MCP startup can remain incomplete. The shutdown executor is bounded but does not supply durable job execution. | Start CPU MCP on the first actual tool call; avoid depending on idle CPU for startup. |

There are no `ensure_future` calls or direct `Thread(...)` constructions in `main.py` or `orchestrator.py`; their relevant detached work is the `create_task` sites above. Ordinary awaited `asyncio.to_thread` calls are request-bound when their caller is request-bound. Gemini prompt-cache lookup/create/delete is synchronous inside an LLM request (`src/backend/llm_gemini.py:62-70`, `src/backend/gemini_cache.py:38-108,225-259`), so it is latency/concurrency work, not a detached loop.

## 8. Increasing concurrency from 2 to about 20

| file:line | What it is | Impact on CPU request-billed API | Suggested fix |
| --- | --- | --- | --- |
| `scripts/deploy_backend_prod.sh:8-10`, `src/backend/mcp_client.py:116-119,566-629` | Current API concurrency is 2; one CPU MCP process uses a request lock for its JSON-RPC pipe. | At 20 requests, tool calls serialize per instance and may wait until the MCP timeout, increasing 503/latency even without GPU. | Load-test simultaneous uploads/chats/quotes; tune CPU worker capacity or admission and timeout before raising concurrency. |
| `src/backend/session.py:578,699-731,764-782,819-878` | Firestore session methods take one process-wide `asyncio.Lock`; several methods perform synchronous Firestore/Storage calls while holding it. | At 20 requests, unrelated sessions queue behind blocking I/O on the event loop. | Move blocking I/O off the loop or narrow lock scope, then measure p95 under concurrency. |
| `src/backend/gemini_cache.py:38-108,225-259`, `src/backend/llm_gemini.py:62-70` | Concurrent cold requests can all miss the process-local prompt-cache map and list/create/delete remote caches. | More duplicate API work and latency; stale-cache deletion can overlap creation. | Serialize or deduplicate creation per cache key and confirm remote idempotency. |
| `src/backend/main.py:1098-1125,2765-2790` | Each Storage audio response downloads the whole object into memory, even for a byte-range request. | Twenty concurrent large audio requests multiply memory/network use. | Stream or range-read from Storage and load-test audio serving memory. |
| `src/backend/main.py:734-859`, `src/api/voicebank_cache.py:784-843` | Uploads and voicebank extraction use local disk in each instance. | Higher concurrent upload/first-call load can exhaust scratch space or contend on a cache directory. | Size scratch/cache for peak concurrency and test simultaneous first requests. |

## Must fix before the API drops its GPU

1. Complete SIG-105's durable one-task-per-synthesis-job worker path, including MIDI, output Storage publication and atomic credit/job finalization. Ensure the API no longer invokes `synthesize` or `save_audio`, and do not cancel an earlier confirmed job.
2. Add and verify `MCP_START_ON_FIRST_CALL` for the request-billed CPU API. Confirm readiness, first tool call, retries and CPU-only imports in the new image.
3. Keep `SESSION_STORE=firestore`, `BACKEND_USE_STORAGE=true`, and shared playback signing credentials. Verify audio, lossless WAV and instrumental MIDI retrieval from a fresh API instance using Storage pointers.
4. Keep export mix disabled until it has a durable execution design; do not remove ffmpeg-related imports while the module still imports `ffmpeg-python`.
5. Load-test the intended ~20 concurrency for serialized MCP calls, Firestore lock contention, prompt-cache cold starts and whole-object audio downloads; set a safe initial CPU API concurrency from measured behavior.
